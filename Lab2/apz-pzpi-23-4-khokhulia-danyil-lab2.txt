ЗАВДАННЯ
     На цій лабораторній роботі потрібно розробити мобільний програмний застосунок для будь-якої поширеної на сьогодні мобільної платформи. Мобільний застосунок повинен бути частиною системи і повинен взаємодіяти з нею. Для реалізації програмного застосунку можна використовувати технології для реалізації програмного забезпечення для мобільних платформ, вказані лектором, а саме Kotlin для Android та Swift для iOS. Звіт повинен містити опис прийнятих інженерних рішень. У ньому повинна бути показана будова мобільного застосунку та його взаємодія з іншими частинами системи.

ОПИС ВИКОНАНОЇ РОБОТИ
     Під час виконання лабораторної роботи було вирішено завдання проєктування та реалізації мобільного програмного застосунку для системи розумного управління громадськими пральнями WashConnect. На цьому етапі розробка зосередилася на побудові клієнтського інтерфейсу для кінцевого користувача, реалізації бізнес-сценаріїв бронювання пральних машин та забезпеченні взаємодії мобільного клієнта із серверною частиною через RESTful API. Розробка велася мовою Kotlin із використанням декларативного UI-фреймворку Jetpack Compose та архітектурного патерну MVVM у поєднанні з принципами Clean Architecture.
     Реалізація мобільного застосунку охопила повний цикл взаємодії клієнта із системою: від реєстрації та авторизації до перегляду доступних пракарень, вибору пральної машини, перегляду тарифів, старту прання та поповнення віртуального гаманця.
     3.1 Архітектура мобільного застосунку
     Архітектура застосунку побудована за багатошаровим принципом із використанням ін'єкції залежностей через фреймворк Dagger Hilt. Структурно проєкт складається з трьох основних логічних шарів:
• Шар презентації (Presentation Layer) реалізований за допомогою Jetpack Compose (Material 3) та містить екрани: LoginScreen, LaundriesScreen, MachinesScreen, SessionScreen, NotificationsScreen та ProfileScreen. Навігація між екранами здійснюється через компонент NavHost із визначеними маршрутами у sealed-класі Screen. Управління станом UI здійснюється через відповідні ViewModel-класи. Стан кожного екрану моделюється через data-класи (наприклад, SessionUiState), а реактивність досягається завдяки потокам StateFlow.
• Шар домену (Domain Layer) інкапсулює чисту бізнес-логіку застосунку. Він містить моделі даних (User, Laundry, Machine, WashSession) та інтерфейси репозиторіїв. Центральним елементом шару є класи Use Cases, які реалізують принцип єдиної відповідальності (SRP) і виконують специфічні бізнес-правила перед зверненням до шару даних.
• Шар даних (Data Layer) абстрагує мережу й локальне сховище. Мережева взаємодія побудована на бібліотеці Retrofit із серіалізатором Gson. Створено ApiService, який мапить ендпоінти бекенду. Для локального збереження JWT-токена та ідентифікатора користувача реалізовано клас TokenDataStore, який використовує Jetpack DataStore Preferences. Окремий перехоплювач AuthInterceptor автоматично додає заголовок авторизації до всіх вихідних запитів. 
  3.2 Реалізація бізнес-логіки мобільного клієнта (Use Cases)
  Бізнес-логіка застосунку реалізована через ізольовані Use Cases, з обробкою помилок за допомогою Kotlin Result<T>.
  3.2.1 Авторизація та управління сесією 
  Класи LoginUseCase та RegisterUseCase відповідають за автентифікацію. Вони інкапсулюють звернення до AuthRepository та обробляють отриманий токен доступу, який асинхронно зберігається у DataStore, що забезпечує автоматичну авторизацію при наступних запусках додатка.
     3.2.2 Розрахунок вартості прання 
     Оскільки система WashConnect підтримує динамічне ціноутворення, логіка розрахунку фінальної ціни винесена у PreviewPriceUseCase. Цей клас звертається до бекенду, передаючи ID пральні та обраного режиму. Повернений об'єкт PricingDetail містить базову ціну, фінальну ціну та застосовані модифікатори, які одразу відображаються клієнту на екрані SessionScreen.
     3.2.3 Управління життєвим циклом сесії 
     Запуск фізичного процесу прання відбувається через StartSessionUseCase. Цей сценарій ініціює запит до API, який перевіряє баланс, блокує кошти та надсилає MQTT-команду на IoT-реле машини. У разі успіху ViewModel оновлює UI, відображаючи картку активної сесії. Механізм скасування (через CancelSessionUseCase) дозволяє користувачу перервати сесію до початку виконання програми.
     3.3 Управління гаманцем та профілем
     Система функціонує за моделлю передоплати. В ProfileViewModel реалізовано логіку перегляду поточного балансу Wallet та його поповнення. При введенні суми та підтвердженні викликається метод репозиторію для проведення транзакції. У разі успіху ViewModel автоматично перезавантажує дані профілю, і користувач миттєво бачить оновлений баланс.
     3.4 UML-діаграми мобільного застосунку
     3.4.1 Діаграма прецедентів
     Побудована діаграма прецедентів відображає повний перелік функціональних можливостей системи. На діаграмі визначено чотирьох акторів: Гість (базовий неавторизований рівень), Клієнт (основний користувач мобільного додатка), Адміністратор та IoT Контролер (апаратна частина). Функціонал Клієнта охоплює авторизацію, бронювання прання (яке обов'язково включає вибір режиму та блокування дверей через зв'язок «include»), а також оплату, що своєю чергою включає перевірку балансу користувача. Адміністратор має розширені права для управління пральнями, машинами та формування звітів. IoT Контролер виступає актором, що ініціює оновлення статусу машини та надсилання Push-сповіщень клієнту.

Рисунок 1 – UML діаграма прецедентів
     3.4.2 Діаграма компонентів
     Діаграма компонентів візуалізує внутрішню архітектуру мобільного застосунку WashConnect та його зовнішні залежності. Застосунок чітко розділений на три шари за принципом Clean Architecture:
• Presentation Layer: містить UI екрани, побудовані на Jetpack Compose, та класи ViewModel для управління станом.
• Domain Layer: ізолює бізнес-логіку у вигляді Use Cases та абстрактних інтерфейсів репозиторіїв.
• Data Layer: містить імплементації репозиторіїв, забезпечує локальне збереження токена (через Jetpack DataStore) та мережеву взаємодію. Взаємодія із зовнішніми системами відбувається виключно через мережевий шар (Retrofit), який спілкується з ASP.NET Core API за протоколом HTTP/JSON, що своєю чергою керує IoT-контролером.

Рисунок 2 – UML діаграма компонентів
     3.4.3 Діаграма діяльності 
     Діаграма діяльності моделює основний бізнес-процес застосунку — бронювання та запуск пральної машини. Клієнт послідовно обирає пральню, переглядає доступні машини та обирає режим прання. Після підтвердження режиму запускається перевірка достатності коштів на балансі користувача. При їх нестачі клієнт перенаправляється на екран поповнення гаманця. При успішному списанні створюється сесія, і сервер відправляє команду на IoT-контролер для активації машини. Процес завершується зміною статусу та генерацією Push-сповіщення клієнту про завершення роботи машини.
 

Рисунки 3-5 – UML діаграма діяльності
     3.4.4 Діаграма огляду взаємодії 
     Діаграма огляду взаємодії візуалізує комунікацію високорівневих компонентів (Mobile App, API Сервер, IoT Контролер) під час життєвого циклу прання. Вона демонструє використання паралельних потоків обробки (fork/join). Наприклад, перед запуском паралельно виконується розрахунок вартості та перевірка доступності машини через IoT. Після успішного запуску система переходить у стан паралельного виконання: IoT-контролер працює і відправляє телеметрію на сервер, тоді як мобільний клієнт знаходиться в режимі очікування завершення на екрані сесії. Паралельні гілки об'єднуються у фінальному блоці закриття сесії.

    1 class TokenDataStore(private val context: Context) {
  2     companion object {
  3         private val Context.dataStore: DataStore<Preferences> by preferencesDataStore(name = "auth_prefs")
  4         private val TOKEN_KEY = stringPreferencesKey("jwt_token")
  5     }
  6     val tokenFlow: Flow<String?> = context.dataStore.data.map { preferences ->
  7         preferences[TOKEN_KEY]
  8     }
  9     suspend fun saveToken(token: String) {
 10         context.dataStore.edit { preferences ->
 11             preferences[TOKEN_KEY] = token
 12         }
 13     }
 14     suspend fun clearToken() {
 15         context.dataStore.edit { preferences ->
 16             preferences.remove(TOKEN_KEY)
 17         }
 18     }
 19 }

Б.3 Програмний код реалізації мережевого перехоплювача для автоматичної JWT-авторизації:
  1 class AuthInterceptor @Inject constructor(
  2     private val tokenDataStore: TokenDataStore
  3 ) : Interceptor {
  4     override fun intercept(chain: Interceptor.Chain): Response {
  5         val requestBuilder = chain.request().newBuilder()
  6
  7         val token = runBlocking {
  8             tokenDataStore.tokenFlow.firstOrNull()
  9         }
 10
 11         if (!token.isNullOrEmpty()) {
 12             requestBuilder.addHeader("Authorization", "Bearer $token")
 13         }
 14
 15         return chain.proceed(requestBuilder.build())
 16     }
 17 }
