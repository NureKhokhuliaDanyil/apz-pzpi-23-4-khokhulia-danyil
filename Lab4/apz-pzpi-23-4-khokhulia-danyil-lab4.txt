ЗАВДАННЯ
     В цій лабораторній роботі необхідно показати як можна масштабувати бекенд системи для роботи із великим навантаженням. Для цього, можна на вибір: 
• масштабувати сервер горизонтально — багато копій сервера виконують однакові функції для різних користувачів; 
• масштабувати сервер вертикально — різні мікросервіси виконують різні функції і масштабуються окремо одне від одного. 
     З технічної точки зору, масштабування можна виконати так: 
• деплой сервера на Kubernetes кластер, разом із окремим load balancer-ом та базою даних. При цьому треба буде показати коректну роботу системи при збільшенні чи зменшенні кількості подів сервера чи окремих мікросервісів; 
•  деплой в serverless середовище (AWS Lambda, Firebase Cloud Functions або аналогічне). Треба показати що система може зменшувати кількість активних інстансів до 0, збільшувати її зі збільшенням трафіку і все ще коректно функціонувати.
•  ваш власний спосіб показати що система може масштабуватись

ОПИС ВИКОНАНОЇ РОБОТИ
     3.1 Опис стратегії масштабування системи
     Для системи WashConnect було обрано стратегію горизонтального масштабування бекенда. Це означає, що замість запуску одного потужного сервера система використовує декілька однакових копій ASP.NET Core API-сервера, які паралельно обробляють запити користувачів. Оскільки основні дані системи зберігаються у спільній базі даних Microsoft SQL Server, API-сервери є stateless (не зберігають критичного стану локально в оперативній пам'яті). Це дає змогу безпечно запускати кілька однакових екземплярів сервера і розподіляти між ними трафік.
     У межах лабораторної роботи масштабування демонструється шляхом локального запуску трьох екземплярів бекенду на різних портах. Для рівномірного розподілу запитів між ними використовується Nginx як reverse proxy та балансувальник навантаження. Для доступу до Nginx із зовнішньої мережі (і для імітації реальних умов тестування) використовується тунель Ngrok.
3.2 Опис технічних рішень
     Для реалізації горизонтального масштабування бекенд на ASP.NET Core було паралельно запущено у трьох різних терміналах з вказівкою різних портів (5001, 5002 та 5003) за допомогою відповідних параметрів команди dotnet run --urls. Це дозволило підняти три незалежні інстанси серверної частини.
     Після цього для Nginx було створено конфігураційний файл, який об'єднує запущені сервери в один пул (upstream) та використовує алгоритм Round Robin для рівномірного розподілу запитів:
Рисунок 1 – Конфігураційний файл для nginx
     Нарешті, для виведення локального балансувальника навантаження Nginx у глобальну мережу було використано утиліту Ngrok. Запуск тунелю командою ngrok http 8080 створив безпечне з'єднання з публічною HTTPS-адресою, через яку згодом виконувалося зовнішнє тестування системи.
     3.3 Аналіз вузьких місць
     Під час горизонтального масштабування API-серверів не всі компоненти системи масштабуються одночасно. При збільшенні кількості реплік бекенду основне навантаження переходить на рівень бази даних. Основні виявлені вузькі місця:
• Підключення до БД: Всі три екземпляри API використовують одну базу даних MSSQL. При пікових навантаженнях може виникнути нестача вільних з'єднань у пулі.
• Блокування записів: При одночасному бронюванні однієї і тієї ж пральної машини різними клієнтами можуть виникати транзакційні конфлікти.
• Пропускна здатність Ngrok: Безкоштовна версія Ngrok має обмеження на кількість з'єднань за хвилину, що може впливати на результати жорсткого навантажувального тестування, відкидаючи частину запитів на рівні тунелю. 
3.4 Опис навантажувальних тестів (Postman Performance Testing)
     Для перевірки продуктивності системи під навантаженням було використано вбудований інструмент Postman Performance Testing. Цей інструмент дозволяє імітувати одночасну роботу багатьох віртуальних користувачів, спираючись на створену колекцію запитів. Сценарій колекції Postman включав наступні запити для перевірки читання даних: отримання загального списку пралень (GET /api/laundries) та отримання деталей конкретної пральні.
     Тестування конфігурувалося для імітації 100 віртуальних користувачів (Virtual Users) протягом 1 хвилини з рівномірним навантаженням. Спочатку запити відправлялися безпосередньо на один екземпляр бекенду (порт 5001), щоб зафіксувати базову продуктивність монолітної системи. Після цього ті самі тести були проведені через порт 8080 (через Nginx), який балансував трафік між трьома екземплярами ASP.NET Core API.

     Результати тестування у Postman наочно продемонстрували ефективність горизонтального масштабування. Використання Nginx для розподілу запитів між трьома репліками дозволило майже втричі зменшити середній час обробки кожного запиту з 29 мс до 10 мс. Крім того, загальна пропускна здатність системи зросла з 1285 до 1438 запитів на секунду. Обидва тести пройшли абсолютно успішно з нульовим відсотком помилок, що доводить надійність та готовність такої архітектури до великих навантажень














ВИСНОВКИ
     Під час виконання лабораторної роботи було успішно реалізовано горизонтальне масштабування серверної частини WashConnect за допомогою Nginx як балансувальника навантаження. Навантажувальне тестування через Postman підтвердило, що використання кількох реплік API значно зменшує середній час обробки запитів та підвищує загальну пропускну здатність системи.
